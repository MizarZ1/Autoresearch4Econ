# 经济与金融实证研究 CLI Agent 开发计划

本计划供后续开发 Agent 直接执行。首版交付一个以 Python 编写、通过 Stata MCP 开展实证分析的 CLI：研究者提供本地数据、研究目标和背景材料，Agent 进行多轮实证分析，在关键判断处等待研究者反馈，最后输出论文初稿以及可复现的分析代码、结果和运行记录。首版保留简洁的分析后端接口；模型生成并实际运行 Python 分析代码的模式安排在下一里程碑，复用研究循环、CLI、状态管理和人工介入机制。

本文描述待实现方案，不代表相关功能已经完成。执行时先检查工作目录和已有实现，再按阶段推进；保留用户已有文件。开发必须遵循分支、提交、测试、审查和 PR 流程，并保留后续迭代所需的模块边界、接口与版本兼容机制，具体见第十四、十五节。

按研究者确认，本项目不受题目建议完成时间约束，以实验室可用首版和工程质量为目标。环境配置、研究案例准备、Stata 方法验证、CI 和审查均纳入开发工作量，分阶段报告实际进展。首版验收以完整 Stata 研究闭环为准，不要求完成下一里程碑的 Python 分析后端。

实施约定：本机 Stata 18、受信任的本地代码执行、由开发方准备公开经典研究案例、使用研究者指定的 Gitea 仓库。题目原文件、压缩包和候选人配套材料只保留在本地，不得提交或上传到 Gitea；具体排除规则见第十四节。

## 一 项目范围与完成标准

### 首版实现范围

- 纯 CLI，不开发网页、桌面界面或终端全屏界面。
- 一次会话处理一个主要研究问题和一份本地分析数据，支持 `.dta` 与 CSV；首版使用 Stata 后端并记录其来源。
- 读取用户提供的数据字典和少量本地背景材料。首版优先处理 UTF-8 文本与 Markdown；PDF 提取不作为必需功能。
- Stata 模式通过通用命令和 do-file 执行接入主流实证方法，不把能力限制为 OLS、面板固定效应和 DiD；具体可用性取决于本地 Stata 版本、已安装扩展与结果读取支持。
- 通过小型 `AnalysisBackend` 接口隔离 Stata 连接与研究循环；首版只实现 Stata，不提前实现 Python 执行器或动态插件系统。
- Agent 自主选择工具和后续分析，完成基准分析与至少一次依据真实结果决定的补充分析。正常演示安排两到三轮研究分析。
- 支持研究设计确认、自然语言修改、拒绝、主动暂停和恢复。
- 真实异步执行两项互不依赖的工作，并保留重叠执行的记录。
- 输出结构完整的论文初稿、结果表及适用时的图形、Stata `.do` 脚本、日志和复现说明。

### 交付里程碑

| 里程碑 | 分工 | 方法范围 | 必需环境 |
| --- | --- | --- | --- |
| M1 首版 Stata MCP | 模型提出设计并生成 Stata 代码，MCP 连接 Stata 执行和读取结果 | 广泛接入 Stata 内置及已安装社区方法，逐项记录验证状态 | 基础模型 API、本地 Python 运行项目、本地 Stata 许可、MCP 服务与所需 ado 包 |
| M2 后续 Python 基础分析 | 模型提出设计并生成 Python 代码，本地 Python 执行器实际运行 | 描述统计、分组比较、相关性、基础检验、OLS、常用稳健或聚类标准误、规模适合的小型固定效应模型 | 基础模型 API、本地 Python 与锁定的分析库；不需要 Stata 或 MCP |

当前开发任务执行 M1；M2 的实现与验收安排见第十一节，不纳入首版完成条件。Python 是首版项目的编程语言，不表示首版已提供 Python 统计分析模式。如果后续确认评审必须在没有 Stata 的环境亲自运行真实 demo，应据此重新安排里程碑；不能仅因连接失败就自行把 M2 提前或替换 Stata 验收。

Stata 的目标方法目录至少覆盖下列家族。目录表示接入范围，不能把尚未测试的方法标成已经验证：

| 方法家族 | 目标方法 | 方法特有的信息和核验 |
| --- | --- | --- |
| 线性与面板 | OLS、WLS、固定与随机效应、高维固定效应 | 样本、吸收维度、聚类层级与自由度 |
| 内生性与动态面板 | IV、2SLS、GMM、动态面板估计 | 工具变量、第一阶段、适用诊断、工具数量与滞后设计 |
| 政策评估 | DiD、分期处理、事件研究 | 处理时点、比较组、估计对象及异质性适用条件 |
| 断点与处理效应 | RDD、匹配、IPW、AIPW | 阈值、带宽、处理分配、重叠条件与权重 |
| 合成控制 | 合成控制及相关扩展 | 供体池、政策前拟合、效应路径与推断方式 |
| 非线性与特殊因变量 | Logit、Probit、Poisson、负二项、Tobit、分位数回归 | 因变量定义、收敛、边际效应或其他目标估计量 |
| 时间序列与持续时间 | ARIMA、VAR、VEC、生存分析 | 频率、滞后、稳定性或生存时间与删失设置 |

方法能力维护三类信息：环境中是否可用、结果是否可规范化提取、具体命令与版本是否通过数值测试。`available_unverified` 不等于 `validated`；缺少命令或前置条件时显示 `unavailable` 并说明原因。通过一个方法代表案例，不能推断整个家族均已验证。

首版以线性或面板、IV、DiD 或事件研究、RDD、非线性模型作为优先验证组；至少包含 IV 和 RDD 两类超出基础回归的真实案例。实施时先用一个已核对的 IV 案例打通完整研究闭环，再补齐优先组，不能把整组方法适配作为首次联调的前置条件。其他家族通过通用执行接入，逐步增加方法规则与测试。未完成的案例单独列出，不重新把产品限制回三种方法。

Stata 官方功能目录包含广泛的计量方法；MCP 的职责是传递命令与读取结果。某些方法或特定实现需要社区 ado 包，运行前检测命令与帮助信息，记录来源和版本；按既定项目依赖策略安装到项目可控位置，不在分析循环中反复升级或修改全局环境。[Stata 功能目录](https://www.stata.com/features/overview/) · [Stata 因果推断方法](https://www.stata.com/features/overview/causal-inference/) · [MCP 工具接口](https://github.com/tmonk/mcp-stata)

### 首版暂不实现

Python 分析后端、数据库接口、大型论文知识库、自动联网文献检索、多用户协作、云部署、通用任务平台、从零重写计量估计器、自动投稿，以及投资策略、因子挖掘和投资研报功能。后续数据库接入可复用输入数据接口，但首版不提前建设连接器系统。

### 首版完成标准

1. CLI 能使用真实模型 API 加真实 Stata MCP 执行完成研究任务，保留一套完整真实运行记录。
2. 项目自己的代码掌握模型循环、工具调度、等待人工和结束任务的决定。
3. 模型能够读取上一轮实际工具结果，再选择下一步；流程中存在由结果决定的分支。
4. 演示至少一次有实质内容的人工修改，并证明后续执行采用了修改后的设计。
5. 演示至少一组真实独立任务的执行时间重叠，不能只用 `async def` 或人为等待模拟。
6. 退出和恢复后，已确认的设计、人工问题、已完成分析和产物仍然可用。
7. 论文中的实证数字能追溯到成功执行且通过必需核验的结果；失败、被取消和过期结果不会混入当前结论。复现包披露全部实质分析与重要设计变更。
8. README、依赖、测试与 Stata 真实运行记录齐全。缺少 Stata 时可继续公共模块开发和离线测试，真实分析与首版整体验收保持待完成；mock 或固定结果不能替代真实运行。
9. 实现位于独立功能分支，有可理解的小批次提交；具备远端时创建 PR，记录审查和 CI 状态，不把本地通过检查写成远端 CI 已通过。
10. 依赖可锁定安装，核心模块可离线测试，外部接口已隔离，运行状态和导出格式有版本号与兼容策略。
11. Stata 方法能力和验证清单准确；`analysis_backend=stata` 写入会话，失败或恢复时不静默切换，公共流程通过简洁接口与执行器隔离。
12. 研究设计、分析尝试、结果产物、人工决定和模型／工具调用可关联追溯；实际重试分别留痕，CLI 和导出可查询调用失败、耗时及已知用量，未知用量不记作零。

这些是本项目的验收标准；其中持久化、结构化结果和论文证据关联是本方案的工程选择，并非题目指定的唯一架构。

### 首个研究案例与验收卡

选定 Acemoglu、Johnson 与 Robinson（2001）《The Colonial Origins of Comparative Development: An Empirical Investigation》的 Table 4，作为第一条 IV 研究闭环。作者档案公开了数据、Stata 程序与 README；数据标签及论文附录 Table A1 可用于编写项目数据字典。[作者数据档案](https://economics.mit.edu/people/faculty/daron-acemoglu/data-archive) · [原论文](https://economics.mit.edu/sites/default/files/publications/colonial-origins-of-comparative-development.pdf)

已检查的 `maketable4.dta` 为 163 行、10 列，`baseco==1` 对应 64 个国家。这是作者整理后的分析数据，不是完整原始历史档案。首版不承担其全部上游数据采集与清洗。

| 项目 | 首个案例的约定 |
| --- | --- |
| 研究问题 | 分析制度保护指标与收入水平的关系，比较 OLS 与 IV，并说明工具变量设计的前提和局限 |
| 基准规格 | `baseco==1`；因变量 `logpgp95`，内生解释变量 `avexpr`，工具变量 `logem4`；规格、样本与推断口径显式记录 |
| 变量字典 | 明确 GDP 对数、征收风险保护指标、定居者死亡率对数和 `lat_abst` 的定义、时期、单位与来源，不只列变量名 |
| 人工修改 | 在首次基准结果后要求加入 `lat_abst` 控制；新设计保留基准与加控制两个比较规格，经确认在当前版本重跑，不直接混用旧版本结果 |
| 后续分析 | 由已观察结果和诊断决定下一步，在已确认范围内选择比较或诊断；涉及样本或识别设计改变时转交研究者，不硬编码所有动作 |
| 数值对照 | 人工核对的独立 Stata 18 参考脚本产生样本量、系数、标准误及诊断；固定推断口径与容差后验收，不以显著性或方向判定成功 |
| 结论检查 | 变量与估计对象正确，区分关联和有条件的因果解释；原论文及其数值是复现对照，不作为识别假设成立的证明 |

阶段 0 完成案例验收卡，保存于 `examples/demo/reference/acceptance.json`，包含数据版本、基准规格、人工修改、合理替代分析边界、数值容差和不得出现的结论错误。固定规格用于检验执行与数值一致性；Agent 提出其他有依据的方案时，单独按设计和证据评价，不强行与不同规格的系数比较。原作者代码和精确参考值仅供开发者与验收器核对，不列入生产任务的可读材料或自动注入模型；若专门提供参考代码开展复现，运行记录明确标注该输入条件。

作者程序含旧 `ivreg` 语法和 Windows 路径。保留原件，在本地副本调整路径；如换用现代命令，核对标准误和自由度处理。阶段 0 用独立的 Stata 参考运行确认基准，不能用 Agent 自己生成的结果同时充当参考答案。

## 三 技术选型与依赖边界

| 部分 | 首版选择 | 职责边界 |
| --- | --- | --- |
| 语言与异步 | Python 3.11+，`asyncio` | 自己实现循环、并发、超时与取消 |
| 模型访问 | 基础 OpenAI-compatible 客户端 SDK | 只发送模型请求，不运行任何 AgentRunner |
| 模型动作校验 | Pydantic 或同等轻量校验 | 校验动作名称和参数，不接管流程 |
| CLI | 标准库 `argparse`，普通逐行输入输出 | 优先保证可用；彩色输出可后加 |
| Stata 连接 | MCP Python SDK 作为协议客户端；优先适配 tmonk/mcp-stata | 只调用底层 Stata 工具，不调用其外部 coding agent 或研究代理 |
| 状态 | 标准库 `sqlite3` | 每个 run 一个数据库，单进程统一写入九张表，事务保存业务状态和调用记录 |
| 文件产物 | 每次执行尝试一个独立目录 | 保存代码、日志和结果；旧产物不被新尝试覆盖 |
| 测试 | pytest 与异步测试支持 | 控制流与故障用 mock；真实连接另做集成验收 |
| 代码质量 | Ruff 格式与静态检查，mypy 类型检查 | 使用统一配置；核心接口具备类型标注，第三方类型缺口仅在适配层局部处理 |
| 环境复现 | pyproject.toml 与一种依赖锁文件 | 公共、Stata 连接及开发依赖分组，记录实际环境；Python 分析依赖在 M2 引入 |
| 初稿与表格 | Markdown 初稿、CSV 表格、可选 PNG 图 | 首版不要求 PDF 或 Word 排版 |

禁止由 LangChain、LangGraph、AutoGen、OpenAI Agents SDK、Claude Agent SDK 等承担核心执行链。普通 MCP 协议库可以使用，但不能把“完整研究任务”作为工具请求转交给另一个现成 Agent。

MCP 版本必须固定并记录，运行时按实际 `list_tools` 结果核对接口，不依赖未经验证的最新接口。tmonk/mcp-stata 当前仓库标注 AGPL-3.0，其文档要求本地 Stata 17+ 与 Python 3.11+；依赖说明中记录来源与许可证，不把第三方服务源码直接复制为项目代码。[工具仓库](https://github.com/tmonk/mcp-stata)

首版只实现 `stata` 分析后端，通过 MCP 执行。MCP 失败时报告连接或运行问题，不自动改用其他计算工具。`AnalysisBackend` 隔离能力查询、数据检查、执行和取消，不要求先实现第二个后端来证明可扩展性。离线控制流测试使用仅供测试的 FakeBackend，不将它作为 CLI 分析模式。若以后增加直接 Stata CLI 连接，应作为 Stata 后端的另一种传输实现单独记录和验证，不新增一套研究循环。

## 四 CLI 使用契约

以下是拟实现的命令，不表示目前已经存在。

```text
econ-agent doctor --backend stata
econ-agent start --backend stata --task examples/demo/task.json
econ-agent resume <run_id>
econ-agent status <run_id>
econ-agent export <run_id>
```

- `doctor` 检查首版所需的 Python 运行环境、模型配置、Stata 与 MCP，显示脱敏结果和缺失项。
- `start` 从任务文件启动；无参数时逐项询问数据路径、研究目标和材料路径。后端取命令行参数，其次任务文件，均未指定时默认 `stata`。首版仅允许 `stata`，显式请求 `python` 或其他值时在创建会话前报错并说明当前支持范围，不展示尚未实现的选择项。
- `resume` 恢复已有会话并保留后端，不重新询问已保存的信息，也不接受覆盖原后端。
- `status` 只读展示状态、当前设计版本、分析进度、等待中的问题，以及调用次数、失败、重试和已知用量摘要；不调用模型，不要求 Stata 或 MCP 可用。
- `export` 整理当前已验证的产物、分析历史和调用摘要，不重新运行分析，也不要求 Stata 或 MCP 可用。默认不包含完整模型请求／响应、秘密配置或备份；导出不是上传操作。

研究者输入在明确的交互点处理。普通自然语言作为对待确认方案的反馈；保留 `/accept`、`/revise <说明>`、`/reject <理由>`、`/pause`、`/stop`。不用再建设聊天前端或全屏 TUI。

运行期间默认自主推进，CLI 只显示步骤、重要发现和任务状态。研究者可用 Ctrl+C 请求暂停，程序先处理在途任务再落盘退出。首版不要求在每条终端输出期间都接收自然语言；暂停恢复后可以补充指令。

`/pause` 保留恢复入口；`/stop` 终止本次会话并导出已有材料。两者都不能让尚未结束的 Stata 任务继续把结果提交为成功。首版没有运行中切换后端的功能；M2 增加 Python 时也应通过新会话切换并记录来源，历史结果始终保留真实后端。

任务文件示例：

```json
{
  "analysis_backend": "stata",
  "data_path": "data/maketable4.dta",
  "dictionary_path": "materials/dictionary.md",
  "material_paths": ["materials/background.md"],
  "research_goal": "分析制度保护指标与收入水平的关系，比较 OLS 与 IV，并说明识别前提及局限",
  "expected_findings": "制度保护可能与较高收入相关，此项为待检验假设",
  "output_language": "zh-CN",
  "max_research_rounds": 3

```

`expected_findings` 可省略。交付形式和预期发现分别存储；不能把“达到期望方向或显著性”作为成功、奖励或停止条件。任务文件中的相对路径以该文件所在目录为基准解析，内部保存规范化路径。

集中管理配置，非敏感项优先级为“CLI 参数 > 环境变量 > 项目配置文件 > 默认值”；task.json 负责研究输入和任务级预算，运行时显式的同名覆盖项优先。配置校验后生成统一对象，业务模块不自行读取散落的环境变量。

环境变量例如 `ECON_AGENT_BASE_URL`、`ECON_AGENT_MODEL`、`ECON_AGENT_API_KEY`。密钥只从环境或不入库的本地秘密配置读取，不接受写入 task.json 或命令行参数；提供不含真实凭证的 `.env.example`，是否自动读取 .env 应在安装说明中明确。固定版本 MCP 的启动命令和参数单独配置。运行记录保留脱敏后的有效配置，不在错误、trace 或提交文件中输出密钥。

## 六 核心数据与状态契约

### 必需对象

| 对象 | 至少保存的内容 |
| --- | --- |
| ResearchTask | schema_version、analysis_backend、数据与材料位置、研究目标、可选先验、交付语言、预算 |
| ResearchDesign | schema_version、设计版本、研究对象、变量含义、样本规则、估计目标、方法、假设、待确认事项；变更理由、相关人工决定与所依据的结果 ID |
| ExperimentSpec | schema_version、analysis_backend、分析目的、设计版本、发起类型、与既有结果的关系、输入、方法、样本、代码语言、预期结果类型 |
| ExperimentResult | schema_version、analysis_backend、experiment_id、attempt_id、可空的 result_id、执行状态、原始产物、可空的规范化结果、提取状态、逐项核验记录、数据与代码 hash、样本信息、估计量与文件引用 |
| HumanRequest | 请求 ID、问题、具体待决定内容、目标设计 ID 与内容 hash、状态、研究者答复 |
| RunState | analysis_backend、当前状态、设计版本、轮次、预算、已完成分析、待处理请求、停止原因 |

首版 `analysis_backend` 固定为 `stata`，同时在读取和创建时验证支持范围。保留该字段用于产物追溯及后续扩展，不预先放行尚未实现的后端。

结果中还应保留实际执行命令、固定效应、标准误处理和聚类信息。每个命名估计量可保存估计值、标准误、置信区间、p 值、自由度与含义；方法不输出系数时使用对应的标量、矩阵、效应路径或表格，不能强行套用 OLS 表格。字段不适用时用 `null` 并解释，不能用 0 表示缺失、未计算或执行失败。

执行成功、结果提取成功和结果核验通过分别记录。合法命令执行成功但暂不能规范化时，保存原始产物并将规范化结果留空，继续提取或排查；不把它改记为执行失败，也不能作为论文实证数字的来源。

每项结果的 `validation_checks` 分三类记录：

| 类别 | 检查内容 | 判定责任 |
| --- | --- | --- |
| 计算与提取一致性 | 原始返回与规范化数值、参数名、样本量、推断方式、文件及输入代码 hash 对应 | 执行器的确定性检查；方法参考样例用于验证提取实现 |
| 研究规格一致性 | 实际使用的变量、样本、估计对象与当前确认设计相符 | 程序核对可验证的返回及执行证据；无法确定的部分标记待判断，必要时交研究者 |
| 方法适用性与解释限制 | 方法前提、实际诊断、未决识别假设和结论措辞限制 | 方法规则、模型审阅及必要的研究者判断，不能仅凭模型肯定回答判为成立 |

每条检查保存类别、名称、`pass/fail/pending/not_applicable`、判定者和依据文件或结果引用；不适用需说明理由。核验必须绑定确切的结果产物 ID、内容 hash、设计 ID 和核验规则版本。重新提取产生新结果版本，重新执行相应核验，不能沿用旧结果的通过标记。只有执行与提取成功、前两类必需检查通过、未存在阻断的方法问题且属于当前确认设计的结果，才可被选入当前论文数值表。未通过的结果保留作排查或历史披露，不改写为成功。

第三类发现明确方法不适用或影响设计的未决问题时，转交研究者，暂不作为当前研究结论；无法用数据直接证明的识别假设应作为假设及局限披露。数值通过不等于因果识别成立，因果或机制表述须与确认设计和实际证据相符。方法目录的 `validated` 仅表示具体命令与版本通过既定测试，不能替代当前研究的核验；首版不建设通用的自动识别证明系统。

### SQLite 表与关联

首版使用九张表：七张研究与运行记录表，加 `model_calls`、`tool_calls` 两张调用记录表。每个 `runs/<run_id>/state.sqlite` 只管理一个 run，RunStore 校验目录与 run 身份一致。数据库是状态及产物索引的权威来源；大文件保存到本地目录，JSONL 和状态 JSON 是可重建的导出材料。研究数据仍是有版本的文件快照，不把整份数据集或每个回归系数拆进这些表。

| 表 | 职责 | 关键字段与关系 |
| --- | --- | --- |
| `runs` | 一次研究会话及当前进度 | `run_id`、状态、后端、可空的 `current_design_id`、任务／配置／输入清单、预算、停止原因、时间；首次确认前当前设计为空 |
| `designs` | 不可变的研究设计内容及确认状态 | `design_id`、`run_id`、版本号、规格 JSON 与 hash、确认状态、变更理由、依据结果 ID；同一 run 内版本唯一 |
| `experiments` | 某一设计下的一项分析规格 | `experiment_id`、`design_id`、目的、`planned/exploratory`、规格 JSON 与 hash、输入快照引用、可空的 `selected_result_artifact_id` |
| `attempts` | 一项分析的每次执行尝试 | `attempt_id`、`experiment_id`、尝试序号、唯一的 `tool_call_id`、执行状态、后端任务／服务身份、取消标记、代码与输入引用、提取状态、结果及核验产物引用、错误、时间 |
| `artifacts` | 文件产物的身份、版本与来源 | `artifact_id`、`run_id`、种类、run 内相对路径、hash、字节数、格式版本、创建时间，以及适用的设计／尝试／调用来源外键；路径在 run 内唯一 |
| `human_requests` | 人工问题、答复及是否已应用 | `request_id`、`run_id`、类型、问题、目标设计 ID 与 hash、状态、答复、创建／答复／应用时间；设计确认必须绑定具体设计 |
| `events` | 追加式状态变化审计 | `event_id`、`run_id`、run 内唯一序号、类型、关联对象外键、简短 payload、时间；不重复存整份提示词和工具输出 |
| `model_calls` | 每次模型 API 请求尝试及其结果 | `model_call_id`、`run_id`、`operation_id`、重试序号、可空的 `parent_tool_call_id`、用途、服务商、请求／返回模型标识、提示与配置版本、请求／响应引用、服务端 ID、状态、解析状态、用量、错误、时间 |
| `tool_calls` | Harness 层每次业务工具调用 | `tool_call_id`、`run_id`、`operation_id`、重试序号、可空的 `source_model_call_id`、供应商工具调用 ID、工具名、参数／返回引用、参数校验状态、执行状态、错误、时间；确定性程序调用可无来源模型 |

主关联为 `runs → designs → experiments → attempts → artifacts`。`model_calls → tool_calls` 关联产生动作的模型请求；工具内部若需要模型，例如两项结果审阅，则由 `parent_tool_call_id` 反向关联其内部请求。不是每个工具都有分析 attempt，也不是每个产物都属于 attempt：输入快照、设计、模型响应和报告都有自己的来源。外键允许尚未产生的结果引用为空，不能使用不存在的占位 ID。

建表及写入时落实以下约束：

1. ID 使用稳定且不复用的标识；外键显式定义，每个连接启用并检查 `PRAGMA foreign_keys=ON`。时间戳统一 UTC，耗时由单调时钟测量。状态用受限枚举，尝试序号及已知用量有合法范围；复杂 JSON 经 schema 校验并保留版本。[SQLite 外键说明](https://www.sqlite.org/foreignkeys.html)
2. 除主键外，约束设计版本、分析尝试序号、事件序号，以及各调用表的 `(operation_id, retry_no)` 唯一。RunStore 在同一事务核对关联对象属于同一 run，选中结果确属该 experiment 的 attempt；不能仅靠任意 ID 存在就接受关联。
3. 设计和分析规格提交后不原地改写；实质修改创建新版本或新 experiment。代码、结果、核验和报告归档后不覆盖，新内容使用新 artifact ID 与路径。`result_id` 就是规范化结果的 artifact ID，不用 experiment ID 代替；不改动计算内容的展示调整可以生成新报告。
4. `selected_result_artifact_id` 是明确选择，不是“最近一条成功记录”。选择时检查执行、提取、核验、取消标记及当前设计；每次报告或导出再次验证。有效性由这些条件统一计算，避免多个表各存一份可能失同步的 `is_valid`。旧设计与旧结果保留，不级联删除研究历史。
5. 人工答复只应用到指定请求及设计 hash，已应用答复重复提交应幂等；过期、被撤销或与当前等待问题不符的答复不能批准新设计。核验变更也保留新记录，不能修改旧检查以掩盖失败。
6. 为实际查询建立少量索引：设计下的分析、分析下的尝试、待答人工请求、调用状态与开始时间、调用来源外键。唯一约束已提供的索引不重复创建；不提前建设跨 run 的统计仓库。

SQLite 使用 `PRAGMA user_version` 记录数据库版本；初次实现直接建立包含九张表的 v1，无须为尚未实现的旧方案编造迁移。实际发生格式升级时按第十五节处理。不建设通用依赖图、数据库服务或重量级迁移框架。

### 模型和工具调用记录

调用监控在 `ModelClient` 和工具调度入口统一完成，不在每个业务方法中手写一套日志。两张表区分调用过程与研究判断：HTTP 成功不等于动作解析成功，工具返回不等于实证核验通过；调用成功也不能直接把 run 改为完成。

- **记录粒度：**`model_calls` 对每次实际 API 请求尝试单独留痕，重试保留原记录，使用同一个 `operation_id` 关联。禁用不可观测的 SDK 隐式重试，或提供可验证的逐次请求钩子；修正提示后重新作决策属于新操作。`tool_calls` 记录 `inspect_data`、`run_analysis` 等业务调用，MCP 内部轮询、取日志只写该调用的诊断，不重复计作业务调用。
- **分析重试：**校验通过并准备启动一次新的 `run_analysis` 时，创建新的 tool call 和 attempt；真正重跑会产生新 attempt。重连、接收旧任务结果或重新提取已保存输出不创建新统计尝试。`inspect_data`、读材料等没有分析 attempt；参数错误的调用仍保留失败记录，但不伪造已执行分析。
- **生命周期：**请求发出前落盘登记，再记录开始、结束、耗时、失败类别及取消信息；崩溃时可保留待发送或状态未知，不能推定请求已到达或未到达服务端。模型传输状态与响应解析状态分别记录，超时、返回无效 JSON、schema 错误和工具执行失败可以分别查询。
- **上下文与产物：**记录请求用途、模型及配置版本、输入设计和结果 ID、工具名及参数、返回与错误的产物引用。脱敏请求／响应保存于本地 `calls/`；凭证、认证头和秘密配置不得写入，长日志不重复放进数据库或事件。不要求额外生成内部思维链。
- **用量与成本：**保存供应商原始 usage，以及可用的输入、输出、缓存和 reasoning 等字段；缺失为 `null/unknown`，不能当作零。统计重试产生的实际用量，缓存或 reasoning 子项不重复加到供应商总量。摘要注明多少次请求缺失用量；成本若展示，只是带币种、价格版本的估算，不能冒充账单。
- **并发与汇总：**两项独立审阅各有模型请求 ID，关联同一 `review_results` 调用，保留真实起止区间。调用耗时与研究总耗时分别展示，不把重叠调用时间相加当作总运行时间。`status` 展示简要计数，`export` 输出带版本的 `calls.jsonl` 和 `usage.json`；模型与工具的失败率分别统计，未终结请求单列。

兼容 DeepSeek 等 OpenAI-compatible 端点时，由适配层映射用量和工具调用字段，保留原始 usage 以应对差异；不得假设所有端点都返回缓存、reasoning 或完整 token 数据。阶段 0 用实际配置验证连接与动作格式，离线契约测试覆盖字段缺失。首版不增加可视化监控平台、独立追踪服务或额外的 token／费用明细表。[DeepSeek Chat API](https://api-docs.deepseek.com/api/create-chat-completion/)

```text
NEW -> RUNNING
RUNNING -> WAITING_HUMAN -> RUNNING
RUNNING / WAITING_HUMAN -> PAUSED -> RUNNING
RUNNING -> COMPLETED
RUNNING / WAITING_HUMAN / PAUSED -> STOPPED
RUNNING -> FAILED
```

`COMPLETED` 仅表示约定的研究流程和产物生成完毕，不表示研究假设得到支持。预算耗尽使用明确的停止原因并导出部分产物，不伪装成完整研究完成。

从 PAUSED 恢复时，若仍有未决 HumanRequest，先恢复到 WAITING_HUMAN；只有不存在未决请求时才进入 RUNNING，不能跳过人工决定。

每个分析尝试的执行状态单独记录 `PENDING`、`RUNNING`、`SUCCEEDED`、`FAILED`、`INTERRUPTED` 或 `CANCELLED`；`SUCCEEDED` 仅表示执行成功，提取和核验仍须分别判断。分析是否适用于当前设计按统一规则计算，并在导出中说明有效或过期原因，不能把历史成功结果物理删除。

### 保存和恢复规则

- 创建人工请求、进入 WAITING_HUMAN 和写入对应事件使用同一事务；应用人工答复、确认确切设计、切换当前设计、更新 run 状态和事件也使用同一事务，不能只保存其中一半。
- 调用前用短事务登记调用记录；分析执行还需关联 attempt、输入与代码产物，随后在事务外调用模型或 MCP。输出先写同目录临时文件，完成后原子改名，再用短事务登记 artifact、结果引用、调用／尝试状态与事件。数据库事务不能覆盖网络等待或整个 Stata 执行期；文件和 SQLite 不是一个跨系统原子事务，不能宣称同时提交。[SQLite 原子提交说明](https://www.sqlite.org/atomiccommit.html)
- 恢复时检查“文件已完成但尚未入库”和“数据库引用文件缺失或 hash 不符”。仅在调用、任务身份与产物证据均匹配时补登记，否则标记待处理；不能仅凭文件存在认定执行成功。缺失或被改动的证据不得用于当前报告。
- 恢复时验证输入 hash。数据改变则暂停并要求确认新输入版本，不能继续沿用原结果。
- 恢复执行时检查持久化后端及其环境；禁止根据当前安装情况改写后端。缺少 Stata 或 MCP 时明确保留待恢复状态，仍可使用 status 和 export 检查已有产物。
- 保留成功尝试，不重复执行。遗留的 RUNNING 尝试先核对本项目后台任务；能够取得已完成且匹配的产物时接收，否则确认为中断后再决定重跑。
- Stata MCP 后端的 task_id 关联创建它的服务实例与会话，新启动的 stdio 服务不能用于查询旧实例的 task_id。保留 cancel_requested 标记，确认旧任务已停止或已排除仍在运行后才允许新建 attempt；无法确定时明确提示并保持暂停，不能直接重复执行。
- Stata 会话内存不是 checkpoint。需要重跑时从保存的输入和 `.do` 脚本新建 attempt，不假设变量、宏或估计结果仍在会话中。
- 迟到的旧任务输出可以归档供排查，但不得解除取消、覆盖当前设计和选中结果或把已停止 run 恢复为运行。关键更新核对预期旧状态及当前执行者，不以“最后写入者”为准。
- 同一 run 只允许一个执行者，使用持有到进程退出的本地排他锁，不能只检查一个容易失效的布尔标记；SQLite 写入由 RunStore 串行协调，只读 status 可以并存。首版不处理多用户协同写入。

## 七 模型循环和工具接口

首版采用统一的结构化动作契约。可以使用基础 API 的原生工具调用，也可以由模型输出经过校验的 JSON；实现时选一种主路径，避免同时维护两套循环。普通文本 JSON 路径不依赖供应商特有的结构化输出功能。

```json
{
  "action": "run_analysis",
  "reason": "检查固定样本下的估计是否变化，以评估样本构成的影响",
  "arguments": {
    "design_version": 1,
    "purpose": "固定样本补充分析",
    "based_on_result_ids": ["art_result_001"]
  }
}
```

这是动作封套示例；具体动作参数由 schemas.py 补齐并校验，不能仅靠自由文本解释执行。记录简短的决策依据即可，不要求模型输出内部思维链。

建议只向模型暴露以下工具，不把整个 MCP 服务器的全部能力直接开放给研究循环：

| 工具 | 输入与输出 | 约束 |
| --- | --- | --- |
| `inspect_data` | 数据 ID，返回变量、样本、缺失和面板结构摘要 | 原始数据保留；只读检查优先 |
| `get_method_help` | 当前后端的方法、依赖和帮助信息 | 检查实际可用性与适用前提，不把目标目录当作已验证清单 |
| `read_material` | 允许的本地文件，返回有来源位置的文本 | 限制长度；数据内容不当作系统指令 |
| `propose_design` | 结构化设计，返回版本与待确认项 | 不直接开始估计 |
| `run_analysis` | 完整规格与当前后端代码，返回执行结果封套、产物与提取核验状态 | 规范化结果允许为空；校验设计、后端和能力，由执行器统一运行和归档 |
| `review_results` | 指定设计和成功结果，返回两项独立审阅 | 使用真实并发，结果供主循环判断 |
| `ask_researcher` | 具体问题、影响、可选建议，返回待处理请求 | 持久化后进入 WAITING_HUMAN |
| `finish_research` | 停止理由、结论草案和证据引用 | 自有控制程序检查条件后决定完成或部分导出 |

主循环必须遵循如下机制，但不把所有研究步骤写成永远顺序相同的固定流水线：

```text
读取状态与当前证据
检查停止条件和预算
请求模型选择一个下一步动作
校验动作与权限范围
执行工具 或 保存人工请求 或 整理交付
保存状态和事件
将真实结果或错误送回模型
再次决定下一步
```

工具错误应形成结构化反馈，如未知工具、无效变量、Stata 返回错误码、连接异常、缺失包、不支持的方法或超时。工具层通过 `AnalysisBackend` 调用已注入的 Stata 执行器，MCP 协议细节不进入研究循环。语法修复可以自动继续；改变研究样本、变量定义或估计目标需要走设计修改流程。同类失败最多自动修复两次，之后明确停止该分析或请求研究者判断。

模型返回的动作、调度器的校验和业务工具执行按第六节关联记录。工具内部的请求关联所属调用，错误反馈引用原调用 ID。只有产出新统计执行的 `run_analysis` 重试才新增 attempt；不要把工具调度、MCP 轮询和模型 API 重试混成同一种研究轮次。

默认设置有限的研究轮数、工具调用次数、模型调用次数和总运行时间，配置中可以调整。技术重试也计入相应调用与时间预算；模型用量按每次实际请求归集，不重复叠加 operation 汇总。发送状态不明的请求保守占用调用预算，其用量仍标为未知。论文写作预留一次模型调用；预算已耗尽时用现有结果生成确定性的部分交付清单，不能为写作重新开启无限循环。

上下文包含当前设计、数据字典摘要、有效结果、重要失败和待处理事项。长日志保存为文件，只把相关片段传给模型；不把整份原始数据全部塞入提示词。

## 八 Stata 执行器的实现重点

### Stata MCP 执行器

执行器必须把“运行代码、等待结束、读取结果、落盘”封装为一个完整操作。主循环不能先独立执行命令，再在其他命令之后随意读取 `e()/r()`。

1. 每项分析从确定的数据快照开始，在独立产物目录保存 do-file 和规格。首次加载完成后，必要的转换应写在代码中，确保可以重新执行。
2. 首版允许使用一个受控 Stata 会话串行执行。会话互斥锁覆盖运行、结束确认、结果读取和落盘。若后来增加 Stata 并发，必须使用不同会话和不同输出目录。
3. 共用执行与原始 `e()/r()/s()` 读取，方法差异由轻量规则描述：所需命令、前置设置、关键输出、字段映射和校验方式。覆盖常见估计类、返回类和自定义表格输出，不假定所有命令都具有 `e(b)`、`e(V)` 或 `r(table)`。
4. 主要估计之后立即保存返回结果。后续统计或检验会覆盖返回值时，拆成独立分析，或在 do-file 内显式保存需要的矩阵和标量。
5. 核对返回命令、变量名、样本量和规格一致性。p 值、区间和标准误采用对应估计方法的推断信息，不能一律用正态近似猜测。
6. 保存原始返回和规范化结果；将 Stata 日志复制到本次尝试目录，不能只保存会消失的临时路径。
7. 超时和 Ctrl+C 先请求取消；未确认终止时记录取消中或中断状态，不能记为成功。必要时只停止本项目独占的会话。
8. 失败时保留代码、日志和错误码，不从日志里挑选部分数字拼成成功结果。自动重试使用新 attempt，旧尝试保留。
9. 方法不在已验证目录时，仍可按通用执行路径运行并保留原始返回；未知结果结构标为未规范化，先补齐提取与核验，再进入论文实证结论。不要仅因缺少预写回归模板而禁止合法的 Stata 方法。
10. `margins`、`estat` 和其他后估计步骤分别保存输出，并声明依赖的主模型；恢复后显式恢复或重跑所需主估计，不能依赖未记录的会话残留。

### 本机执行与数据保护

研究者已选择在本机直接执行模型生成的 Stata 代码，接受首版不提供严格文件隔离。首版采用数据副本、备份、执行日志和核验，不增加每次代码执行的人工审批；研究设计改变仍按第九节处理。

加载用户数据时先记录原始文件 hash，建立独立备份和本次 run 的输入快照，分析代码使用快照或其工作副本。备份与原件不作为模型的默认输入路径，不覆盖既有备份。执行前后核对原件及快照完整性；发现异常立即停止、记录受影响文件并提示从备份恢复，不悄悄覆盖用户文件。备份与用户原始数据保持本地，不进入 Git。

项目在工具入口校验声明的输入、输出路径，归档时只接收本次 attempt 的产物，并将输出位置写入生成代码的约定。MCP 与 Stata 子进程只传入运行需要的环境变量，排除模型 API 密钥及其他无关凭证。保存实际执行代码、标准输出或 Stata 日志、错误与产物清单。

工作目录、路径校验、代码检查和 hash 检查可减少或发现误操作，但不能阻止任意 Stata 代码访问当前用户有权限访问的文件；不将上述措施称为安全沙箱或强访问限制。代码模板可用于已验证方法，不能把模板目录当作 Stata 的全部能力边界。首版不建设虚拟机或容器执行平台。

## 九 真实异步与人工介入

### 首版并发方案

优先选择对同一份已保存结果开展两项独立审阅：一项检查结果与研究设计是否一致，另一项解释结果并提出有依据的后续分析。两个任务各自使用一次基础异步模型请求，通过 `asyncio.gather(return_exceptions=True)` 或等价方式并发，各自设置超时并归档结果，汇合后由主循环决定下一步。不能因一项抛出异常就丢失另一项已完成的结果。

这样无需为满足异步要求并发修改同一个 Stata 会话。两项审阅有不同的输入指令和输出职责，但都没有自己的 Agent loop，不引入现成多 Agent 框架。

设置并发上限 2，每项审阅分别写入 `model_calls`，关联同一 `review_results` 的 `tool_call_id`，记录开始与结束时间、成功或失败状态。某项失败时，保留另一项结果并明确缺失内容；不得捏造第二份审阅。证明并发的真实 trace 必须来自实际请求，单元测试中可以用同步屏障检验调度，不能用人为 sleep 冒充真实并发工作。

如果真实模型端点只允许单请求，可在可用环境下改为两个独立 Stata 会话或另一组真实独立 I/O 任务；必须在 README 中写清实际采用的方案和证据。

### 人在回路的具体行为

首次研究设计完成后展示简短方案并等待确认；已经确认范围内的补充分析与纯代码修复自动执行。实质改变样本、变量定义、估计目标或识别设计时，再请求研究者判断。

- 同意：记录研究者输入，解锁对应设计。
- 修改：将自然语言转换为结构化改动，展示改动及其影响；有歧义时继续澄清，修改明确时进入新版本确认。
- 拒绝：记录理由，禁止执行被拒绝方案；返回设计修订或结束。
- 暂停：保存请求与设计，退出后仍可恢复到同一问题。

人工请求在创建时就写入 SQLite，不能只保存在一个内存 Future 中。处于 WAITING_HUMAN 时不执行依赖该答复的分析，也不让模型自行代替研究者确认。

研究设计更新采用简单的保守规则：先生成不可变的新版本并请求确认；未获确认前不能按新设计执行。确认答复绑定其 ID 和 hash，在事务内切换 `current_design_id`；切换后旧版本分析和论文不再作为当前证据，重新执行当前版本所需分析。纯展示修改不使统计结果失效。首版不建设复杂依赖推导，旧版本材料作为历史保留。

实质分析在规格中标记 `planned`（首次确认设计已约定）或 `exploratory`（看到结果后提出），技术重试沿用原规格，以 attempt 区分。设计变更保存理由、研究者决定及影响该变更的结果 ID；没有对应结果时明确留空。新增分析不能事后改标为首次设计已约定。

## 十 论文初稿与交付材料

`paper.md` 至少包含研究问题、背景与假设、数据与变量、实证设计、主要结果、补充分析、讨论与局限、参考材料。最终初稿面向研究者，隐藏无助于理解研究的程序细节；执行编号和 trace 放在证据清单与复现说明中。

论文生成分两步：程序从当前有效的结构化结果渲染表格和图形引用；模型依据这些结果撰写文字。重要实证数字可使用由程序填充的占位符，减少手写数字错误。每项实证结论关联结果 ID 和表格位置，保存在 `evidence.json`。

输出前按第六节检查引用的实验执行、提取和逐项核验状态、当前设计、文件及关键数字。模型审阅不能覆盖程序核验失败。仅有原始输出而未完成提取核验的分析可以列入待处理事项，不能进入实证数字。没有被执行的机制检验只能写为待检验解释；未解决的识别条件写入局限。缺少可靠文献材料时明确保留文献补充项，不生成不存在的论文或引用。

复现包从已有实验和事件记录导出 `analysis_history.csv`，列出全部实质分析的目的、设计版本、发起类型、执行状态、当前有效性及未纳入结论的原因，并引用各次技术尝试。不支持假设或未达显著性的成功结果不得仅因此省略。正文简要说明重要的结果驱动变更，旧结果仅作为明确标记的历史披露，不混入当前结论，也不要求正文展示全部历史表格。

不要求首版验证所有自然语言句子的语义正确性。对关键结论进行人工抽查，在 README 中明确自动检查的边界。

最终产物包括：

- 论文初稿、对应结果表及适用时的图形。
- 每次分析的 `.do` 脚本、日志、原始返回与规范化结果，标明 Stata 环境与方法验证状态。
- 当前设计和历史修改、人工答复、事件记录，以及 `analysis_history.csv`。
- `calls.jsonl` 与 `usage.json`：模型／工具调用的关联、状态、耗时、重试和用量缺失情况，默认不导出完整提示词、响应及秘密配置。
- `reproduce.md`：实际后端、输入来源、环境版本、依赖包和从数据到结果的重跑步骤。
- Stata 重跑入口或脚本清单；能够从新 Stata 会话重建已交付结果。

## 十一 按顺序执行的开发阶段

阶段 0 至阶段 7 构成 M1 首版开发范围，不按题目建议时长设硬截止。最先验证实际环境和案例，然后按最小完整研究流程推进；阶段 2 只需跑通首个 IV 案例，不要求先完成全部方法验证。每阶段同步开发实现与测试，完成检查、差异审阅和小批次提交后继续；其余优先方法组在阶段 7 前半段补齐，仍属于 M1 正式验收范围。

公共模块只实现一次，首版通过简洁接口接入 Stata。环境未就绪时，可以使用测试替身开发控制流、状态与报告；真实分析、真实模型加工具的演示及首版整体验收仍须等待 Stata MCP 可用。完成 M1 后交付首版，不自动继续执行 M2。

功能阶段可以归入一个持续更新的首版 PR，不要求每个阶段创建一个 PR。开发 Agent 可以并行处理互不依赖的小模块；多个执行者使用不同分支或 worktree，集成者负责合并和验证，避免同时修改核心状态和接口。

| 阶段 | 依赖 | 主要交付 | 阶段验收 |
| --- | --- | --- | --- |
| 0 环境验证与工程基线 | 无 | 环境实测、AJR 验收卡、题目文件排除、Git 分支与检查入口 | 记录实际环境状态和独立参考运行；确认 Gitea 条件与本地排除规则 |

### 阶段 0 环境验证与工程基线

第一步执行第二节的环境实测：选择项目 Python，验证 Stata 18 许可与最小计算、pystata/MCP 兼容及真实返回、模型请求和并发、Gitea 访问与已有历史。用临时工作区和测试数据做探测，不修改用户原始文件。记录确定的问题后再选择依赖版本，不把缺失环境留到最终演示时才发现。

准备 AJR 作者数据、项目自编字典和验收卡。以独立 Stata 参考运行固定基准及加纬度规格的数值、标准误口径、容差和关键解释检查；这是开发验收依据，不新增生产执行后端。作者原文件留在忽略目录，检查下载 hash，保留路径适配差异。各方法 ado 的逐项验收可在后续扩展时完成。

核对本地文件排除规则，再按第十四节沿用远端历史或建立空仓库基线及功能分支。建立虚拟环境、最小 pyproject、锁文件、统一离线检查入口与 Gitea 工作流；创建简短 CONTRIBUTING.md 和 PR 模板。用可运行入口及有意义的冒烟测试跑通安装和检查，不用空测试或永久跳过制造绿灯。无需安装 M2 的分析依赖。

完成信号：环境检查和独立参考结果有真实记录，案例验收卡固定，题目原文件不在暂存区或待推送历史中；分支、基线提交和离线检查入口可用。模型、Stata、远端和 CI 状态分别报告。缺少环境时继续不依赖它的工作，相关真实验收仍为待完成。

### 阶段 1 对象与状态

定义动作、设计、尝试结果、人工请求与调用记录结构，包含后端、方法能力和多种结果形态；明确模型、分析执行器和存储的小接口，按第六节初始化九张表的 SQLite v1。实现外键、唯一性与状态约束、必要索引、不可变产物、输入与代码 hash、短事务及排他锁，建立 run 目录。同步测试后端持久化、关联约束、确认的幂等与版本绑定、文件与数据库中断恢复、格式版本和未来版本拒写；不加入通用工作流引擎。

完成信号：同一任务保存、关闭、恢复后状态一致；错误关联被拒绝，旧设计批准不能解锁新设计，中断不会留下可误用的成功结果，不覆盖已有尝试和归档产物。

### 阶段 2 首个 Stata 执行闭环

先定义 `AnalysisBackend` 的 `inspect_data`、能力与方法帮助、`run_analysis`、取消和归档契约。按第八节实现 Stata 执行器，核心循环只依赖该接口；测试替身与真实执行器复用相同结果类型。

先跑通 Stata 通用执行、帮助查询、原始返回及 AJR IV 案例所需的结果提取与核验。接入 `tool_calls`，关联分析 attempt、代码、结果与核验产物；轮询不新增业务调用，重跑保留旧 attempt，重新提取创建新结果版本并重新核验。处理数据副本、超时、取消、错误对象和日志归档，每个案例记录实际命令与版本。其余方法先登记可用性，完整方法验证移至阶段 7，不阻塞模型循环联调。

完成信号：AJR 基准 IV 实际执行并与阶段 0 独立参考数值核对，核验状态和证据可读取；执行器能返回明确失败，原始数据未被覆盖。随后立即进入阶段 3，避免先横向适配全部方法。

### 阶段 3 自有研究循环

实现工具描述、动作校验、按方法能力的工具分发、结果反馈、自动修复上限和停止条件。把 Stata 方法能力、数据摘要、当前设计和有效结果放入上下文。用 mock 完成控制流验证，再接入真实 Stata 执行“基准结果返回后选择补充分析”；mock 结果不能作为真实演示证据。

在模型适配层接入 `model_calls`，逐次记录请求、重试、传输／解析状态及原始与规范化 usage，关联产生的工具动作和所依据结果。禁用或捕获 SDK 隐式重试；测试成功响应中的非法动作、超时、未知用量及凭证脱敏。兼容端点按实际配置验证，不把配置可填等同于接口已通过。

完成信号：保存的 trace 能指出哪一项结果触发了哪一项后续分析；换用不同的工具反馈时，测试能够验证反馈实际进入下一轮请求，不能只有固定动作列表。

### 阶段 4 有界并发

基于阶段 3 的真实结果并发调用两项审阅，限制并发数，各请求独立落盘并关联父工具调用及输入结果。处理超时与局部失败。此阶段不增加独立 Agent runtime。

完成信号：两项任务的起止区间重叠，记录包含实际请求与输出。异步单元测试用屏障证明并发启动，避免靠脆弱的耗时阈值判断。

### 阶段 5 CLI 与人工恢复

接通命令与自然语言反馈，明确拒绝尚未实现的后端。完成首次设计确认、修改、拒绝、Ctrl+C 暂停、resume 和 status。人工修改影响设计版本和实际代码；答复和设计切换遵循同一事务，重复或过期答复不误推进。恢复时保留 Stata 后端、处理遗留任务，不重复运行已完成尝试；status 从数据库只读汇总调用信息。

完成信号：在等待人工时退出，恢复后仍显示原问题和后端；研究者修改样本规则后，实际 `.do` 与结果使用新规则，旧报告不可作为当前产物导出。

### 阶段 6 论文与复现包

从明确选中、通过必需核验的当前结果生成表格，组织论文初稿并建立精确到 artifact ID 与 hash 的证据引用。生成分析历史、调用与用量摘要、复现说明和 export 命令；核对摘要与逐次记录一致，未知用量显式保留。报告每次生成新版本，默认导出排除完整模型请求／响应。未完成的分析进入局限或待办，不进入已完成结果。

完成信号：首个案例贯通模型、人工修改、补充分析和输出，从全新 Stata 会话重跑关键结果在验收卡容差内一致；不合格结果不能进当前表格，历史分析仍可追溯。随机过程固定并记录种子，其他方法的非系数输出随阶段 7 验证。

### 阶段 7 方法扩展与首版交付

在首个完整闭环已可用的基础上，补齐线性或面板、IV、DiD 或事件研究、RDD、非线性优先验证组，为每个具体命令、版本和结果映射提供小型数值参考，验证非系数输出。IV 与 RDD 均须真实运行；这些方法用各自适合的数据或明确标注的合成测试数据，不将所有方法套到 AJR 数据上。通用接入仍可处理其他方法，未验证状态如实登记。

汇总检查并完成 AJR 的真实模型加 Stata 演示，按验收卡核对研究对象、数值、人工修改与结论依据。保留真实人工输入，测试中的脚本化反馈另作标注。整理 README、来源获取说明和方法清单，检查所有待推送内容，按第十四节更新 Gitea PR、检查 CI 并处理审查意见。Python 模式列入 M2，不作为首版缺陷。

完成信号：验收记录对每项需求给出命令、文件路径或事件位置，PR 内容与最终实现一致。准确分别报告代码完成、测试通过、真实运行、审查、CI 和合并状态；缺项显式保留，不能用文字说明代替真实执行。

### M2 后续增加 Python 基础分析模式

M2 在首版交付后另行安排，不由阶段 7 自动启动。开始时从最新基线建立独立功能分支和 PR，复用已验证的研究循环、人工介入、状态与报告逻辑，不重建一套 Agent。若明确的无 Stata 真实演示要求改变优先级，应先同步本计划的范围和验收标准。

方法范围为描述统计、分组比较、相关性、基础检验、OLS、常用稳健或聚类标准误，以及规模适合的小型固定效应模型。使用锁定的 pandas、NumPy、SciPy、statsmodels 等成熟库，绘图按需添加。基础范围是产品选择，不表示 Python 无法实现复杂方法。

实施顺序与要求：

1. 添加 `python_backend.py` 和独立分析依赖组，通过现有 `AnalysisBackend` 接入。先用已核对脚本验证读取、估计和导出，再接模型生成的 `analysis.py`；不在 CLI 主进程中直接 `exec` 模型代码。
2. 每个 attempt 使用独立工作目录和新进程，由自有异步 subprocess 执行。归档代码、stdout、stderr、退出码、依赖版本、原始产物与规范化结果；实证数字来自真实执行，模型直接填写的数值不能充当计算结果。
3. `.dta` 读取保留标签、分类、日期和缺失值语义，CSV 明确类型和缺失编码，两种格式均有真实读取测试。使用成熟估计器；样本规则、截距、协方差、自由度及固定效应规模限制进入规格。
4. 校验实际样本量、估计对象、参数名、推断方式、有限数值和文件一致性，用已核对的小样例进行真实数值测试，不能只检查退出码。超出能力范围时返回限制，不自动安装任意依赖或启用 Stata。
5. 实现超时、取消、进程回收和恢复。子进程状态与 run、attempt 关联，不能只凭可能复用的 PID 判断；未确认旧任务停止时不重试。内存不充当 checkpoint，重跑从输入与脚本开始。生成脚本不接收模型密钥，原始输入保留，输出限定在本次工作区；不把普通子进程称为完整安全沙箱。
6. 开放 `--backend python` 并增加独立 doctor、能力提示、环境记录和复现说明。Python 模式不导入、不启动、不探测 Stata 或 MCP，恢复保持原后端；切换需新建会话并记录来源，失败不静默换后端。
7. Python 真实离线计算与无 Stata 环境安装、模式隔离测试加入默认 CI。新增后端涉及公共逻辑时补充 Stata 回归验证，保留首版会话兼容性；发生实际格式变化时再增加迁移。

M2 完成标准：在没有 Stata 的环境，用真实模型加实际 Python 执行完成多轮分析、实质人工修改、真实并发、暂停恢复和论文导出；新进程能重跑结果。FakeBackend 仍仅用于测试。若用相同基础模型做跨后端核对，先对齐样本、编码、截距、协方差与自由度约定，不承诺不同方法天然等价。交付单独的 Python 真实记录、测试结果、依赖与能力清单，并按第十四节完成 PR 和审查。

首版使用真实模型与 Stata MCP 完成以下演示：

2. 启动研究任务，读取数据与背景，生成并由研究者确认设计 v1。
3. 执行 AJR 基准分析，展示主要结果和分析依据。

具备指定 Gitea 远端和写权限后，推送功能分支并尽早建立草稿 PR；按实例能力使用草稿状态或标题标记，不用 GitHub 专用命令冒充 Gitea PR。首版可以采用一个持续更新的 PR，内部保留清楚的提交历史；独立功能变大时拆成有明确依赖的小 PR，不为每个函数或每个开发阶段强行创建 PR。

PR 描述包含实际解决的问题和行为变化、实现范围、测试命令及结果、真实运行证据位置、兼容性影响和未完成项。范围变化时同步重写标题与描述。存在迁移时说明升级与回退方法。使用仓库模板，没有模板则采用上述结构。

## 十五 支持持续迭代的工程约定

### 模块边界与扩展位置

保持单进程 Python 项目。CLI 只处理输入、输出和应用组装；研究循环负责业务状态和决策；工具层把业务动作交给外部适配器。模型 API、MCP 与 SQLite 的具体字段和连接逻辑不进入核心研究规则，外部适配器不得反向导入 CLI。

使用少量 `typing.Protocol` 或等价的小接口，构造时注入实现，不引入依赖注入容器：

| 边界 | 首版接口职责 | 后续迭代方式 |
| --- | --- | --- |
| ModelClient | 异步请求、逐次调用观测、返回项目动作或统一错误与 usage | 更换兼容模型服务时只修改配置或适配层，字段缺失不破坏公共契约 |
| AnalysisBackend | 能力与方法帮助、数据检查、执行和取消；返回执行状态、原始产物、可空的规范化结果及提取核验状态 | 首版实现 Stata MCP；M2 通过同一边界增加 Python，无须重写研究循环 |
| RunStore | 加载状态，事务保存关联对象、调用与事件，登记产物，应用人工请求及选择有效结果 | 状态实现或格式升级不影响 CLI 的研究语义；调用记录复用该存储，不新增监控数据库 |
| 数据入口 | 将输入转换为有来源和版本信息的数据快照 | 后续数据库接口产出相同快照契约，不让数据库查询散入循环 |

首版只实现 Stata MCP 后端，延迟创建连接，将外部依赖限制在适配层；离线测试、status 和已有结果 export 不因 Stata 环境缺失而失败。新增方法时扩展能力规则、代码生成提示或模板、特殊结果映射与测试，通用 Stata 执行无需每个方法新增一个工具。不在 CLI、循环和报告中到处追加同一个方法分支，不建设动态插件市场，也不提前添加空的 Python 执行器。

代码应有清晰类型和边界错误：配置错误、工具执行错误、模型响应错误、状态版本错误与用户停止分别处理。保留原始异常作为诊断依据，对使用者输出可操作的信息，不使用吞掉所有异常的兜底“成功”。

### 版本与状态兼容

区分应用版本、持久化 `schema_version`、数据库版本与研究设计版本；它们不能共用一个字段。将应用版本、Git 提交和工作区是否有未提交代码记录到运行环境清单，便于定位实际执行的代码。

初始数据库版本按第六节九张表建立 v1，无须编造不存在的历史。发生真实格式变化时增加编号迁移函数和上一格式的测试 fixture，升级前使用一致性备份，事务内执行迁移，失败回滚；遇到比程序更新的数据库版本拒绝写入并给出清楚提示。只读 status 不隐式执行迁移，不能通过删库让旧会话“兼容”。

任务、设计、结果和导出清单保存 `schema_version`。读取旧格式时使用明确的转换函数，或清楚告知不支持的版本，不按新格式静默解释。对外字段删除、语义变更和 CLI 破坏性修改应在 PR 和 CHANGELOG 中说明，提供迁移或明确的保留旧版本运行方法。

首版不引入 Alembic 等重型迁移框架，但迁移入口、未来版本拒写和只读行为从第一版就有测试。恢复、人工决策和有效结果选择规则集中实现，避免 CLI 与报告各维护一套判断。

### 测试分层与回归

| 层次 | 执行环境 | 内容 |
| --- | --- | --- |
| 单元测试 | 离线，无 Stata 和密钥 | 循环、预算、配置、人工决策、恢复、取消、结果选择、调用汇总与脱敏 |
| 契约测试 | 离线，固定的脱敏输入及临时数据库 | MCP 结果、模型动作与 usage、九表关联和事务、产物核验绑定；fixture 注明来源和版本 |
| 外部集成测试 | 明确启用，有本地真实工具 | Stata 调用、各方法结果提取、取消及必要的模型接口探测 |
| 完整演示 | 真实模型与 Stata MCP | 完成多轮研究、人工修改、并发、恢复及最终交付 |

默认检查不联网。外部集成测试通过显式命令或标记启用；若要求执行却缺少配置，应报告未执行或失败，不能当作通过。Mock 验证控制行为，不能替代实际计算准确性的验收。

优先覆盖状态转换、失败和恢复等高价值行为，不用固定高覆盖率数字替代测试质量。每次发现实际缺陷补充能复现该缺陷的回归测试；新增方法补充预先核对的数值样例与适用条件测试。

### 环境与运行可复现

选择一种依赖管理和锁文件方案，开发机与 CI 按同一文件安装；首版按公共、Stata 连接和开发用途分组，外部 Stata 与 ado 包单独记录。Python 分析依赖组在 M2 增加，届时支持不安装 Stata 连接依赖的独立运行。新增依赖说明用途，不为小功能引入完整 Agent 或工作流框架。

首版运行清单保存应用与 Git 版本、analysis_backend、Python 运行时、模型标识、脱敏配置、输入 hash、随机种子，以及 Stata、MCP、ado 包版本或来源。M2 的 Python 会话另存分析库版本。数值重跑使用预先约定的容差，不承诺远端模型每次生成完全相同的文字或行动序列。

按第六节通过 run、design、experiment、attempt、artifact、human request、model call 和 tool call ID 串联记录。事件负责状态变化，调用表负责请求、重试、耗时和用量，产物表负责文件来源；不在多处重复维护相同统计。调用摘要从数据库计算，缺失用量保持未知，费用估算标明口径。终端输出与日志分开，不向使用者暴露无关的内部状态细节。

后续发布以通过验收的提交为基准维护版本号与 CHANGELOG；需要正式发行时再按用户指定渠道创建版本标签和发布。首版不自动上传包仓库、发布网站或建设复杂发布平台。
